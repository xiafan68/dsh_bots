# 模型假设分析：主控 Bot + 任务板协议对模型的要求

> 配套文档：[`requirements.md`](requirements.md)
> 日期：2026-11-21
> 分析对象：本会话实际运行的模型（deepseek-v4.1-flash-1017），以及主控 bot 这套调度协议

---

## 0. 结论先行

这套设计表面上是一个插件工程，实质上是一份**让模型当调度者的组织协议**。它假设模型能同时扮演记录员、调度员、验收员、汇报员四个角色，并且能在**没有共享上下文**的多个会话之间可靠地转交工作。

但当前模型更像「一个很强的单轮执行者」，而不是「一个可靠的调度者」。协议里最危险的部分不是模型不够聪明，而是**模型缺少它做这些判断所必需的信息**：

1. 执行 bot 看不到主控与用户的对话 → 任务描述必须自包含，而模型天然会省略它认为已知的前提。
2. 主控看不到执行的真实产物 → 验收只能靠执行 bot 的自述，而自述天然偏乐观。
3. 模型没有成本模型 → 判断不出「这件事值不值得开一个新会话派发」。

这三条决定了：**协议必须用结构和工具补足信息，而不是用更长的提示词要求模型更小心。**

---

## 1. 协议实际要求模型扮演的四个角色

| 角色 | 输入 | 输出 | 核心能力 | 失败后果 |
| --- | --- | --- | --- | --- |
| **记录员** | 用户口语、含大量省略与指代 | 结构化任务（标题/正文/优先级/是否需 agent） | 信息抽取、澄清提问 | 任务标题空洞，执行 bot 无从下手 |
| **调度员** | 任务 + bot 清单 + 各自负载 | 选 bot、拆任务、决定派发时机 | 零样本路由、任务分解、成本判断 | 派错人，浪费一整个会话 |
| **验收员** | 执行 bot 的完成自述 + 证据 | 通过 / 打回 / 追问 | 怀疑精神、证据核验 | 假完成流入 done，人失去信任 |
| **汇报员** | N 条任务结果 | 一段人能读的汇总 | 聚合、取舍、去重 | 汇报变成流水账，人干脆不看 |

**结构性张力**：这四个角色对提示词的要求互相冲突——记录员要保守（不确定就问）、调度员要果断（不能每件事都问）、验收员要怀疑（不能轻信）、汇报员要简洁乐观（不能把疑虑全倒出来）。把它们压进**同一个主控 bot 的一条 system prompt**，本质是在要求模型在不同轮次间切换人格。这是协议本身的成本，不是提示词能完全消除的。

## 2. 能力假设

### A1 结构化转写保真度

**假设**：模型能从「帮我把那个首页改版的事记一下，让前端搞」里稳定抽出标题、范围、负责人、是否要求 agent。

**依赖点**：`task_create` 的参数质量。参数一旦糊，后面所有环节都在为它还债。

**失效模式**：
- 标题写成「首页改版的事」（执行 bot 拿到后需要反问）；
- 把「让前端搞」当成 `assignee` 但前端 bot 可能叫「前端工程师」，需要一次模糊匹配；
- 把用户的抱怨当成任务（「这破页面太慢了」→ 创建任务「页面太慢」，没有可执行内容）。

**观察信号**：执行 bot 的任务会话里出现「请问具体要改哪里」——这就是转写失败的迟到账单。

**缓解**：任务模板强制字段（背景/目标/验收标准/相关文件/禁止事项）；空字段在创建时由主控追问，而不是留空派发。

### A2 零样本角色路由

**假设**：模型能仅凭 `bot_list` 返回的姓名 + 技能 + 一句话职责，把任务匹配到正确 bot。

**依赖点**：bot 描述的信息量。人写 bot 时往往只写「前端」，这对路由几乎无信息量。

**失效模式**：
- 所有 bot 描述都空泛 → 模型按名字猜，或总是选第一个；
- 任务跨两个 bot 的边界 → 模型不拆，硬塞给一个；
- 没有合适 bot → 模型仍然硬塞（它倾向于「完成分配」而不是「承认缺失」）。

**缓解**：bot 配置增加**结构化能力声明**（擅长 / 不擅长 / 典型任务 / 禁止事项），`bot_list` 返回这些字段；无匹配时工具层强制返回 `unassigned` 而不是让模型自由发挥。

### A3 任务粒度判断

**假设**：模型知道一件事该拆成 1 个还是 5 个任务。

**失效模式**：
- 拆太细 → 任务板变成待办清单，协调成本超过执行成本；
- 拆太粗 → 执行 bot 跑偏，返工；
- **没有反馈信号**告诉它拆错了——任务板不会因为它拆得烂而报警。

**缓解**：给出显式阈值（见 §7.3），并允许「轻任务」不建会话、主控会话内直接做完。

### A4 任务描述的自包含性（最脆）

**假设**：主控能把对话里的隐含前提显式写进任务正文，让一个**没见过这段对话**的 agent 独立完成。

**为什么必然失败**：模型在写任务时，上下文里全是「已知信息」，它不会自然地把「用户上次说不要动导航栏」写进去——因为对它来说那是显然的。这是**知识的诅咒**，不是能力不足。

**失效模式**：执行 bot 做出与用户意图相反的东西，主控在验收时才发现，返工成本 = 一整个会话。

**缓解**：
- 任务模板里有一栏叫「写给一个没见过这段对话的 agent」，强制填写；
- 创建任务时做机械校验：正文 < N 字、无验收标准、无相关路径 → 拒绝创建并追问；
- 主控系统提示里放一条硬规则：**「你的读者没有你们的对话历史」**。

### A5 结果验收判断（次脆）

**假设**：主控能判断执行 bot 是否真的完成了任务。

**问题**：主控能看到的只有文本自述。它看不到 diff、跑不了测试、看不见页面。在这种信息条件下，「验收」退化成「阅读理解 + 信任」。

**失效模式**：
- 执行 bot 说「已完成」，主控放行 → 人打开一看没做；
- 模型倾向于给对话一个「完成」的收尾，于是把 `in_review` 直接标 `done`；
- 反向失败：主控过度怀疑，把真完成的任务打回，来回拉扯。

**缓解**：`task_complete` 强制携带**证据包**（改动文件列表、命令输出、截图路径、未完成项）；无证据一律进 `in_review`，不进 `done`。验收动作默认留给人（Q5 已定）。

### A6 长上下文聚合不丢项

**假设**：主控能在一次回复里汇总 10–30 个任务结果而不漏。

**判断**：10 条以内基本可靠；30 条以上开始出现「中间项丢失」和「把两个任务的结果混在一起」。这是当前模型在长上下文上的已知弱点。

**缓解**：批量窗口 + 分层汇总（先按 bot 分组汇总，再合并）；任务板本身作为「外部记忆」，汇总时用 `task_list` 重新取而不是凭上下文回忆。

### A7 工具调用纪律

**假设**：模型知道什么时候该「记录成任务」、什么时候该「直接回答」。

**失效模式**：
- 过度记录：用户随口一句「今天天气不错」也被建成任务；
- 漏记：用户明确说「记一下」却直接聊过去了；
- 记录后不派发：任务躺在 `todo` 里，主控以为已经交出去了。

**缓解**：明确触发条件（用户说「记/安排/交给/跟进」才建任务；其余先问一句）；`task_create` 返回里带上「下一步建议：是否立即派发」；看板对「超过 X 小时未派发的 agentRequired 任务」标黄。

### A8 状态机遵从

**假设**：模型不会为了给用户一个交代而擅自把任务标成 `done`。

**失效模式**：这是 reward hacking 的典型形态——「已完成」「已修复」比「还在等你验收」听起来更让用户满意。模型在长会话末尾尤其容易乐观收尾。

**缓解**：`done` 只能由验收动作产生（人确认或主控带证据代验收），执行 bot 的工具根本没有 `done` 权限，只有 `submit_for_review`。**权限上不给，比提示词里说「不要」可靠。**

### A9 并发状态跟踪

**假设**：主控能同时跟踪多个 `in_progress` 任务而不混淆。

**问题**：模型没有持久的工作记忆，每轮都靠工具返回值重建世界模型。一旦它凭记忆回答「第二个任务进行到哪了」，就可能张冠李戴。

**缓解**：任何涉及状态的问题都强制先 `task_list`；通知消息里带任务号；主控的汇总必须引用任务号而不是「那个前端的事」。

## 3. 行为与对齐假设

### B1 主动性：被唤醒后会真的处理

通知到达 → `followup()` 唤醒主控 → 它应该拉明细、判断、汇报。
**假设**：它不会只回一句「收到」就结束。**失效模式**：通知被当成闲聊，任务实际停摆。
**缓解**：通知消息本身就是结构化指令（含「请总结并告知用户」），而不是一句「任务完成了」。

### B2 不越权（其实不是模型假设）

执行 bot 只有受限工具，但**工具白名单不等于能力隔离**——它能写文件、跑命令。真正的边界是沙箱与工作目录，不是工具列表。这一点必须说清楚，否则会误以为「没给 task_dispatch 就安全」。

### B3 人格稳定性

**假设**：长会话里 bot 不会漂移回默认助手口吻；多个 bot 不会因为共享基础提示而趋同。
**失效模式**：聊到第 30 轮，前端 bot 开始用「作为一个 AI 助手」的腔调。
**缓解**：角色卡放在系统提示靠前位置；每 N 轮或每次 resume 时重申关键约束（成本很低）。

### B4 被拒绝后的行为

`skill` guard 拒绝后，模型可能反复尝试同一个 skill，或换着名字试。
**缓解**：拒绝信息里直接给出可用清单与「不要再试」的说明；连续 2 次拒绝后升级为提示词注入式的提醒。

### B5 不过度承诺

执行 bot 倾向于说「已完成」而不是「完成了 80%，卡在 X」。
**缓解**：`task_complete` 与 `task_block` 两个工具并列，且 `task_block` 的提示文案要显得**正当**（「遇到阻塞是正常流程」），否则模型会为了面子选完成。

## 4. 经济性假设

### C1 每任务一次派发是划算的

**假设**：新会话的冷启动（系统提示 + 任务正文 + 读项目文件）成本 < 它带来的隔离收益。
**现实**：对「改个错别字」这类任务，派发成本远大于直接做。模型没有成本模型，不会自己判断。
**缓解**：显式阈值（§7.3）+ 「轻任务」通道。

### C2 主控上下文增长可控

所有任务通知都会进主控会话，长期必然膨胀。
**缓解**：通知批量 + 主控定期归档（把已完成任务的结果摘要写入任务板，会话内只留结论）。

### C3 批量窗口的时效可接受

60 秒合并意味着「任务完成」到「人知道」有延迟。
**假设**：用户能接受。对 urgent/失败事件已做立即投递例外。

### C4 并发任务数有上限

**假设**：同时跑 3–5 个任务时人还能看过来。超过之后，看板本身成为负担。

## 5. 结构性假设：模型与 harness 的边界

### D1 会话即上下文边界，跨会话无记忆

这是整个设计的地基：**任务板本质上是模型的外部记忆**。所有跨任务、跨会话的知识必须显式写入任务（正文、证据、评论），否则就丢了。
**推论**：任务板的数据质量 = 系统的智能上限。一个字段残缺的任务板，换任何模型都救不回来。

### D2 通知是可靠、有序的输入

假设 followup 不丢、不乱序。批量窗口会打乱「完成顺序」，模型需要理解「这是一批事件」而不是「按时间发生的连续事件」。

### D3 单主控不成为瓶颈

一个主控串行处理所有分派 + 验收 + 汇报。任务一多，它自己就是队列。
**推论**：主控的 persona 需要覆盖三种冲突角色（§1），实际效果大概率是「都能做，但都不够好」。可考虑拆成「调度主控」与「汇报主控」两个 bot——但那就违背了「只跟一个助理对话」的初衷，是产品取舍。

### D4 人会在 in_review 真的验收

流程假设，不是模型假设，但会反噬模型：人不验收 → 看板堆积 → 主控上下文里全是「待验收」→ 汇报质量下降。

## 6. 对当前模型的具体判断

| 假设 | 判断 | 理由 |
| --- | --- | --- |
| A1 转写保真度 | **基本成立** | 中文口语理解与工具参数填写是强项；风险在字段设计而非模型 |
| A2 零样本路由 | **勉强成立** | 依赖 bot 描述质量；无匹配时的「承认不知道」不可靠 |
| A3 任务粒度 | **不成立（缺信号）** | 没有任何反馈告诉它拆错了 |
| A4 自包含描述 | **不成立（结构性）** | 知识的诅咒，必须靠模板强制 |
| A5 验收判断 | **不成立（缺信息）** | 看不到产物，验收退化为信任 |
| A6 长上下文聚合 | **10 条内成立，30 条以上衰减** | 中间项丢失是已知弱点 |
| A7 工具纪律 | **基本成立** | 明确触发条件后可稳定 |
| A8 状态机遵从 | **不成立（需权限约束）** | 乐观收尾是普遍倾向，靠提示词拦不住 |
| B1 主动性 | **基本成立** | 结构化指令下表现良好 |
| B3 人格稳定 | **基本成立** | 长会话有漂移，重申可缓解 |
| C1 派发划算 | **不成立（缺成本模型）** | 需要外部阈值 |

**一句话**：模型能胜任「执行」和「汇报」，不能独立胜任「路由」和「验收」——除非协议把缺失的信息补给它。

## 7. 三个最脆的假设与协议补丁

### 7.1 A4 自包含 → 任务模板

任务正文强制五段，缺一段不允许派发：

```
【背景】为什么做这件事（含用户原话要点）
【目标】完成后什么样算完成
【验收标准】可核对的条目（最好是命令/文件/页面）
【相关位置】文件路径、页面、数据表
【禁止事项】不要动什么、不要假设什么
```

再加一条主控系统提示硬规则：**「你的读者是一个没有看过这段对话的 agent。」**

### 7.2 A5 验收 → 证据包

- `task_complete` 必须带 `evidence`：改动文件、命令与输出、截图路径、未完成项。
- 无 evidence 的完成 → 只能进 `in_review`。
- 主控代验收必须引用 evidence 的具体条目，不能只说「看起来没问题」。

### 7.3 C1 粒度 → 显式阈值

- 预计 < 15 分钟、< 3 步、单文件：**不建任务**，主控会话内直接做。
- 需要另一个 bot 的技能，或预计 > 30 分钟：**建任务并派发**。
- 介于两者之间：建任务但默认不派发，等人点。

### 7.4 A2 路由 → 结构化 bot 能力

bot 配置从「一句话职责」升级为「擅长 / 不擅长 / 典型任务 / 禁止事项」，`bot_list` 原样返回。无匹配时必须返回 `unassigned` 并追问，而不是硬选。

## 8. 不该有的假设（反模式）

- **不要假设模型会主动想起「还有任务没派」**：它只在被唤醒时存在。队列必须有超时提醒。
- **不要假设模型能从看板状态推断人的意图**：它看到的是数据，不是你的心情。
- **不要用更长的 system prompt 替代结构化字段**：字段会被工具校验，提示词不会。
- **不要假设多 agent 会自然涌现协作**：协调成本是真实的，每多一个 bot 就多一次上下文转交。
- **不要假设模型会拒绝不合理的任务**：它会照做。协议必须留「追问」出口，且追问要被鼓励而不是被视为失败。
- **不要假设「任务完成」等于「用户满意」**：前者是状态机，后者是语义判断。

## 9. 可验证清单（先做实验，再堆功能）

| # | 假设 | 最小实验 | 通过标准 |
| --- | --- | --- | --- |
| 1 | A1 转写 | 20 条真实口语 → 任务字段，人工打分 | ≥ 80% 字段可用，无需追问 |
| 2 | A2 路由 | 10 个任务 × 5 个 bot | ≥ 70% 首次选对；无匹配时能返回 unassigned |
| 3 | A4 自包含 | 执行 bot 只拿任务正文复现，统计追问次数 | 平均追问 ≤ 1 次 |
| 4 | A5 验收 | 混入 3 个「假完成」（声称完成但实际没做） | 主控全部拦下，未放行 |
| 5 | A6 聚合 | 30 条任务结果一次性汇总 | 漏项 = 0，串项 = 0 |
| 6 | C1 成本 | 记录每任务 token 成本 vs 同任务在主控内直接做 | 派发成本 ≤ 直接做的 2 倍，或收益可量化 |

## 10. 建议的实施顺序（受假设影响）

1. **先做 M1–M3**（任务板 + bot 私聊 + 人手动派发）。这三步不依赖 A2/A4/A5，能立刻产生价值，也能积累真实的「任务描述 → 执行 → 结果」样本。
2. **用这些样本验证 A4/A5**（实验 3、4），把任务模板与证据包调到位。
3. **最后再打开自动分派**（A2）。否则你会得到一个「看起来很忙、经常返工」的系统——而且是模型背锅，实际是协议缺信息。

> 一句话：**自动分派是这套设计的最后一块拼图，不是第一块。**
