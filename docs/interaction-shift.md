# 交互形态变迁分析：从「人建会话指派」到「主控 Bot + 任务板」

> 配套文档：[`requirements.md`](requirements.md) · [`model-assumptions.md`](model-assumptions.md)
> 日期：2026-11-21
> 问题：过去是人给每个任务新建一个 session 来指派 agent；现在改成「跟主控 bot 说 → 主控记任务并分派」。这个变化在交互、任务类型、模型依赖上意味着什么？是否适合所有任务？

---

## 0. 结论

1. **这不是换了个入口，而是把三件人类工作转移给了模型**：调度（选谁做）、上下文搬运（把前因后果讲给执行者）、初筛验收（判断做没做好）。三项里有两项模型目前做不好，而且不是「更聪明」能解决的——缺的是信息结构。
2. **适合的任务有明确边界**：可提前完整描述 + 完成可由产物验证 + 时长大于调度成本 + 失败可回滚。反过来，探索型、审美型、强上下文型、超小型、高危型都不适合直接派发。
3. **最优形态不是二选一**，而是「**会话 → 任务**」的晋升：先在会话里谈，谈清楚了再把这段对话沉淀成任务派发。这同时消掉描述成本和知识诅咒（下文 §8，本次分析最重要的建议）。

一句话：**新形态不是「更自动」，而是把人从执行期挪到定义期和验收期。它奖励好的需求描述和好的验收标准，惩罚含糊。**

---

## 1. 两种形态对照

| 维度 | 人建 session 指派（旧） | 主控 bot + 任务板（新） |
| --- | --- | --- |
| 工作单元 | 会话 | 任务 |
| 指派方式 | 人选 agent（本身就是一次判断） | 人选「要不要派」，主控选谁（人可覆盖） |
| 上下文载体 | 会话内隐式、连续 | 任务正文显式、自包含 |
| 监督方式 | 实时旁观，边看边纠 | 异步看板 + 完成通知 |
| 纠偏时机 | 对话中即时 | 验收时集中（成本高一个量级） |
| 反馈时机 | 即时 | 批量、有延迟 |
| 并行度 | 人串行切换（人是瓶颈） | 天然并行（review 容量是瓶颈） |
| 状态存储 | 人脑 + 会话列表 | 任务板（人和 agent 共享的世界模型） |
| 可追溯性 | 翻聊天记录 | 结构化活动日志 |
| 人的主要负荷 | 操作 + 记忆 | 描述 + 验收 |
| 失败发现 | 立刻，成本低 | 延迟，成本高 |
| 适合规模 | 任意，受注意力限制 | 中大型、可分解、可验证 |

## 2. 交互层面的六个改变

### 2.1 委派对象上移：从「选执行者」到「选要不要委派」

旧形态里，「这个任务给前端 agent」本身就是人的一次判断，也是人对系统的理解方式。新形态把这次判断交给了主控，人只决定「值不值得开一个任务」。

- **收益**：人不需要记住有哪些 bot、各自擅长什么；新增 bot 不需要改人的习惯。
- **新成本：信任税**。人不知道主控为什么选了 A 不选 B，一旦选错一次，就会退回手动模式。
- **失效模式**：主控选错且给不出理由 → 人对整个自动化失去信任。
- **对策**：分配时附一句理由（「这个任务涉及 CSS，交给前端」）；一键改派；改派后记住偏好（同类任务下次优先）。

### 2.2 工作单元从「叙事」变成「记录」

会话是叙事：前因后果在对话流里，指代有上下文。任务是记录：必须自包含。

- **收益**：可检索、可并行、可审计、可恢复、可交接。
- **成本**：所有隐性上下文必须显式化。以前「你懂的」就够了，现在必须写下来。
- **失效模式**：任务正文空洞 → 执行 bot 跑偏 → 返工，而且返工发生在另一个会话里，人看不见过程。
- **对策**：五段模板强制；从会话晋升（§8）。

### 2.3 监督从「过程」变成「结果」

旧形态人是旁观者，看到不对可以立刻喊停。新形态人只在两个时刻出现：派发前（定义）和完成后（验收）。

- **收益**：不必守着，可以去做别的事。
- **成本**：失去中途纠偏能力；人必须有能力「验」，而验收比旁观难。
- **失效模式**：`in_review` 堆积成人肉瓶颈；或者人懒得验，直接点通过，质量失控。
- **对策**：证据包（改动/输出/截图/未完成项）；高风险任务强制人 gate；抽样验收代替全量验收。

### 2.4 反馈从「即时」变成「批量延迟」

- **收益**：不打断，适合并行。
- **成本**：时效性下降；**汇报质量直接决定信任**。
- **失效模式**：汇报写成流水账（「任务 A 完成、任务 B 完成、任务 C 完成」）→ 人绕过主控直接看会话 → 主控退化成通知器。
- **对策**：分层汇总（先结论，再异常，最后明细）；只报「需要人决策的」和「失败的」；每条附证据链接。

### 2.5 并行度上升，人变成多路复用器

- **收益**：吞吐提升，长任务不再阻塞人。
- **成本**：人的 review 容量成为新瓶颈；上下文切换有认知成本。
- **失效模式**：同时开 10 个任务，全部卡在「等你」，人直接不看板了。
- **对策**：WIP 限制（同时 `in_progress` ≤ 3–5）；看板显示队列长度；「等你」列按紧急度排序而不是按时间。

### 2.6 状态外化：任务板成为共享世界模型

- **收益**：人和 agent 看到同一份状态，减少「我以为你在做」的错位。
- **成本**：看板可能与真实状态漂移（任务显示 `in_progress`，但会话早死了）。
- **失效模式**：人信了看板，实际任务停摆三天。
- **对策**：租约心跳；无活跃租约的 `in_progress` 标灰并提示「可能已中断」；定期对账。

## 3. 人的角色变化

| | 旧形态 | 新形态 |
| --- | --- | --- |
| 角色 | 操作者：开 session、选 agent、喂上下文、盯着 | 需求方 + 验收方 + 异常处理方 |
| 核心技能 | 会切 tab、会复制粘贴上下文、会看进度 | 会把事说清楚、会看证据、能容忍异步 |
| 时间分布 | 主要花在执行期 | 主要花在定义期和验收期 |
| 消失的工作 | — | 上下文搬运、tab 切换、进度记忆 |
| 新增的风险 | — | 描述不清、验收不严、失去掌控感 |

**关键推论**：如果一个人在「定义」和「验收」上不投入，新形态会比旧形态**更慢**——因为多了一层转述和一层等待。旧形态里含糊是可以被对话修复的，新形态里含糊会变成返工。

## 4. 任务类型适配矩阵

用两个轴判断：**可提前描述性**（能不能在动手前说清楚）与 **可产物验证性**（做完能不能被客观检查）。

```
                 可验证性 高
                      │
   ② 先会话后任务      │   ① 甜区：直接派发
   （需求还在聊）      │   （明确 bug、加接口、写脚本、批量改）
                      │
 ─────────────────────┼─────────────────────  可描述性
                      │        高
   ④ 不要派发          │   ③ 派发但要人验收
   （战略讨论、审美定调）│   （设计初稿、文案、调研报告）
                      │
                 可验证性 低
```

### 4.1 逐类判断

| 任务原型 | 适配度 | 推荐形态 | 理由 |
| --- | --- | --- | --- |
| 明确的 bug 修复 | **强** | 任务派发 | 描述便宜、结果可验（测试/复现步骤） |
| 边界清晰的新功能 | **强** | 任务派发 + 检查点 | 可拆、可验；但要在中途设检查点防跑偏 |
| 重构 / 迁移 | **中强** | 拆成多个任务 + 分阶段人 gate | 单个任务太大，必须拆；不可逆步骤要人确认 |
| 调研 / 方案评估 | **中** | 派发一次，要「选项 + 建议」不要「结论」 | 结论依赖人的偏好；要求给出取舍而不是替人拍板 |
| 设计 / 文案 | **中弱** | 会话迭代为主；任务只承载「出 3 版初稿」 | 验收靠品味，需要多轮对话 |
| 强上下文（「接着刚才那个改」） | **弱** | 留在会话 | 跨会话转交成本 > 收益 |
| 超小任务（改错别字、看个报错） | **弱** | 直接做，不建任务 | 调度开销 > 执行开销 |
| 高危不可逆（删数据、发版、改生产配置） | **弱**（除非有 gate） | 任务 + 强制人审批 | 不能无人值守；任务板适合做审批 gate |
| 大规模同构（100 个文件各改一遍） | **强，但形态不同** | subagent 并行，而非多个 bot 会话 | 适合 fan-out，不适合多轮对话 |
| 需要人的外部动作（打电话、当面确认） | 取决于工具 | 任务 + 人作为 assignee | 不是任务形态问题，是能力边界 |

### 4.2 三条硬规则（可以直接做成产品里的提示）

1. **30 秒能自己做完的，别建任务。**
2. **需要边做边看才能判断对不对的，用会话，不要派发。**
3. **失败不可逆且没有审批 gate 的，不要无人值守派发。**

### 4.3 收益公式（用来做「要不要派」的判断）

```
派发收益 ≈ 人省下的监督与搬运时间 − (描述成本 + 验收成本 + 返工期望)
```

- **描述成本** ≈ 你要写多少字，才能让一个没见过这段对话的 agent 接手；
- **返工期望** ≈ 描述不清的概率 × 返工成本；
- 小任务里「描述成本 + 验收成本」经常直接吃掉全部收益，这就是它们不适合的原因。

## 5. 对模型能力的增量假设

只列「人退出中间」之后**新增**的依赖——也就是原本由人承担、现在由模型承担的部分。

| 原本由人承担 | 现在由模型承担 | 新增依赖的能力 | 当前模型判断 |
| --- | --- | --- | --- |
| 把前因后果讲给执行者 | 写出自包含任务 | 视角转换（知道读者不知道什么） | **弱**：知识的诅咒，需模板强制 |
| 判断该找谁 | 路由到 bot | 零样本匹配 + 承认「没有合适的」 | **中弱**：描述空泛就靠猜 |
| 判断做没做好 | 预验收 | 证据核验、怀疑精神 | **弱**：看不到产物，退化为信任 |
| 决定值不值得开会话 | 判断派发成本 | 成本模型 | **弱**：模型没有这个概念 |
| 中途喊停 / 纠偏 | 异步异常处理 | 主动上报、表达不确定 | **中弱** |
| 同时记住多件事 | 跟踪多任务状态 | 依赖工具返回值重建世界模型 | **中**：强制先查询可缓解 |

### 5.1 最关键的新增假设：**主动澄清**

旧形态里误解的成本很低——人说一句「不是那个页面」就修好了。新形态里误解的成本是一整个会话的返工，而且人在验收时才发现。

所以新形态要求模型在**信息不足时停下来问**，而不是「先做再说」。而当前模型的行为偏置恰恰是后者：它倾向于给出一个可交付的结果，而不是承认自己没听懂。这是这套交互最需要对抗的倾向。

### 5.2 第二关键：**校准的置信度**

主控必须能说「我不确定该给谁」「这个结果我没法验证」。模型普遍过度自信，而人会把这种自信当成事实——汇报里一句「已完成，测试通过」，人就不会再去看。**过度自信的汇报比没有汇报更危险。**

## 6. 三个最容易翻车的交互点

### 6.1 第一句话就被当成任务

用户说「首页有点慢」，主控立刻建任务「优化首页性能」并派发。执行 bot 拿到的信息量为零，只能瞎猜。

**对策**：主控的默认动作是「复述 + 问一个最关键的问题」，而不是「创建任务」。只有信息足够时才建任务；不够时先追问，追问不算失败。

### 6.2 汇报看起来完成了，实际没有

这是 A5 在交互层的投影。人只看汇报，不看会话，所以汇报的可信度就是系统的可信度。

**对策**：汇报强制两栏——「我验证了什么」/「我没验证什么」。前者给证据，后者给风险。人一眼能看出哪里需要自己看。

### 6.3 人不知道「现在到底在干嘛」

异步执行最大的心理成本是失控感。看板只显示状态，不显示进展。

**对策**：每个 `in_progress` 卡片显示「最近一次活动时间 + 当前步骤」；超过 N 分钟无活动标黄；点开直达会话。

## 7. 是否适合所有任务：直接回答

**不适合。** 而且不是「暂时不适合」，是结构性的：

- **描述成本随任务变小而相对变大**：小任务的收益是负的。
- **验收成本随主观性上升而变大**：审美类任务的验收无法外包给模型，最终仍要人逐轮看。
- **上下文依赖随对话深度上升**：越「接着刚才说」的任务，跨会话转交越亏。
- **风险随不可逆性上升**：没有 gate 的自动化在高危任务上是负资产。
- **探索型任务的路径本身是产物**：中途的方向调整需要人参与，一次性派发会得到一个「正确但没用」的结果。

反过来，**适合的任务有共同结构**：边界清楚、产物可查、失败可回滚、规模大到值得一次转述。

## 8. 最重要的建议：会话 → 任务的晋升机制

如果只能改一件事，改这个：**任务的主要来源不应该是「新建任务」表单，而应该是「把一段对话沉淀成任务」。**

做法：

1. 人和某个 bot（通常是主控）在会话里把事情聊清楚；
2. 点「沉淀为任务」，由**拥有完整上下文的那个 agent** 按五段模板写出自包含 brief；
3. 人只做确认和微调（改几个字，而不是从零写）；
4. 任务创建后进入看板，再派发给执行 bot。

为什么这能同时解决三个问题：

- **描述成本**：从「写一段 brief」变成「确认一段 brief」；
- **知识诅咒**：写 brief 的 agent 刚刚就在对话里，它知道哪些前提是隐含的——而且它可以把「用户原话」直接引用进去；
- **探索型任务**：允许先用会话探索，收敛后再转成任务，而不是逼人一上来就写清楚。

**推论**：`task_create` 工具退居次要场景（用户口述、没有现成会话时）；「沉淀为任务」成为主路径。新建任务表单仍然保留，但不再是默认入口。

## 9. 怎么验证「适合度」（不要凭感觉）

记录每个任务的全生命周期人时：

| 指标 | 含义 |
| --- | --- |
| 描述用时 | 从想到说清楚花了多久 |
| 执行时长 | 派发到完成 |
| 返工次数 | 被打回或人工修正的次数 |
| 验收用时 | 人看证据 + 判断的时间 |
| 主观评分 | 人对结果的满意度和对过程的信任度 |

按任务原型分组，比较「任务形态总人时」vs「直接在会话里做的总人时」。**如果某类任务在任务形态下更慢，就把它从派发清单里删掉**——这不是模型不行，是这类任务本来就不该被派发。

## 10. 一页总结

| 问题 | 回答 |
| --- | --- |
| 改变了什么 | 调度权、上下文搬运、初筛验收从人转移到模型；工作单元从会话变成任务；监督从过程变成结果 |
| 人的角色 | 从操作者变成需求方 + 验收方 + 异常处理方；时间从执行期移到定义期和验收期 |
| 对模型的新依赖 | 自包含转写、零样本路由、证据核验、成本判断、主动澄清、校准置信度——后两项最缺 |
| 是否适合所有任务 | 否。适合可描述、可验证、规模够大、可回滚的任务；不适合探索、审美、强上下文、超小、高危 |
| 最该做的一件事 | 会话 → 任务的晋升机制，让有上下文的 agent 来写 brief |
| 最该防的一件事 | 第一句话就被当成任务；以及过度自信的完成汇报 |
